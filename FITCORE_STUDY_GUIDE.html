1. The 60-second pitch

FitCore ERP is a gym / fitness-facility management system. It manages five business modules — DashboardMembershipSalesPaymentInventory — over a single SQL Server database, exposed through two independent front ends that share one business core:

  • a Windows Forms desktop app (ERP_Project1) used by front-desk staff, and
  • an ASP.NET Core REST API (ERP_api) that exposes the same operations over HTTP, consumed by a Blazor WebAssembly client (ERP_UI) and usable by any future mobile app.
The single most important architectural point to make in your presentation: the business logic lives in neither front end. It lives in ERP_infrastructure (services + repositories) on top of ERP_domain (entities). The WinForms app and the Web API are both thin clients of that core. Add a mobile app tomorrow and you write zero new business rules.

4. Where MVC fits (the honest answer)

Be precise here — panels love this question. FitCore is not a textbook ASP.NET MVC application. There are no Views/ folders, no Razor .cshtml pages rendered server-side, and no ViewBag. It is an N-tier / Clean-style layered architecture, and each of its three front ends uses a different MVC-family pattern on top of that shared core. Saying "it's MVC" without qualification is the trap; saying the following is the strong answer.

4.1 The Model–View–Controller mapping, per front end

WinForms Member entity + MemberService + MemberRepository Form1.Designer.cs — the DataGridView, textboxes, buttons Form1.cs — the btnAdd_Click / btnUpdate_Click / btnDelete_Click event handlers MVC-derived Document–View: View and Controller are fused into the Form class (classic for desktop UI), but the Model is fully separated.
REST API Entities + services; DTOs as the wire model The JSON response body (there is no HTML view — the client renders) The lambda registered by app.MapPost("/fitcore/3/members", …) in Program.cs API / Minimal-API MVC: "View" degenerates into content negotiation. Each endpoint delegate is a controller action.

4.2 The line to say out loud

"FitCore separates Model (domain entities + services + repositories) from View (forms, JSON, Razor) with a Controller layer in between (form event handlers on the desktop, minimal-API endpoint delegates on the web). Because the Model layer sits in its own class library, the same Model is driven by three different controllers. That's the payoff of MVC applied at solution scale, rather than the ASP.NET MVC project template."

4.3 Proof that the separation is real, not cosmetic

The clinching example: the rule "a member with history cannot be deleted" is written once, in MemberService.DeleteMemberAsync. Both controllers consume the same MemberDeleteResult enum and merely translate it into their own idiom:

// The Model decides. ERP_infrastructure/services/MemberService.cs
public async Task<MemberDeleteResult> DeleteMemberAsync(int id)
{
    var member = await _repository.GetByIdAsync(id);
    if (member == null) return MemberDeleteResult.NotFound;

    var history = await _repository.GetHistoryCountsAsync(id);
    if (history.HasAny) return MemberDeleteResult.HasHistory;

    var deleted = await _repository.DeleteAsync(id);
    return deleted ? MemberDeleteResult.Deleted : MemberDeleteResult.NotFound;
}
// Controller A — the web. ERP_api/Program.cs
return result switch
{
    MemberDeleteResult.Deleted    => Results.NoContent(),        // HTTP 204
    MemberDeleteResult.HasHistory => Results.Conflict(...),      // HTTP 409
    _                             => Results.NotFound()          // HTTP 404
};

// Controller B — the desktop. ERP_Project1/Form1.cs
switch (result)
{
    case MemberDeleteResult.Deleted:    MessageBox.Show("Member deleted."); break;
    case MemberDeleteResult.HasHistory: MessageBox.Show("…set status to Inactive instead."); break;
    default:                            MessageBox.Show("That member no longer exists."); break;
}

Same decision, two presentations. That is exactly what the C in MVC is for.

StockMovement — the audit-trail pattern worth highlighting

StockMovement records BalanceAfter on every row. That turns inventory into an append-only ledger: you can reconstruct the stock level at any past moment and explain why it changed (Reference = "SALE-42", "VOID-42"). Most student projects only store the current quantity — this is a genuine differentiator to point out.

6.2 Fluent API configuration (code-first)

All mapping is done in OnModelCreating, delegated to one private method per aggregate — ConfigureMembers, ConfigureSubscriptions, ConfigureSales, ConfigureSaleItems, ConfigurePayments, ConfigureProducts, ConfigureInventory, ConfigureStockMovements, ConfigureSuppliers. No data-annotation attributes are used on the entities, which is what keeps ERP_domain free of an EF Core dependency.

private void ConfigureMembers(ModelBuilder builder)
{
    builder.Entity<Member>(entity =>
    {
        entity.HasKey(x => x.MemberId);
        entity.Property(x => x.FirstName).HasMaxLength(100).IsRequired();
        entity.Property(x => x.Phone).HasMaxLength(20).IsRequired().HasDefaultValue("");
        entity.Property(x => x.Status).HasMaxLength(20).IsRequired().HasDefaultValue("Active");
        entity.Property(x => x.JoinDate).IsRequired().HasDefaultValueSql("GETUTCDATE()");
    });
}

Three configuration techniques are on display, and each is worth one sentence in the presentation:

  • HasMaxLength / IsRequired → generates NVARCHAR(100) NOT NULL instead of NVARCHAR(MAX). Storage and index efficiency.
  • HasPrecision(18, 2) on every money column (Price, Amount, TotalAmount, UnitPrice) → DECIMAL(18,2). Never float for currency.
  • HasDefaultValueSql("GETUTCDATE()") → the database stamps the time, so rows inserted by a script or by SSMS are still valid.

6.3 Delete behaviour — the most interesting design decision in the schema

RelationshipOnDeleteWhy
Subscription → MemberCascadeDeleting a member removes their subscriptions.
Subscription → PlanRestrictA plan in use cannot be deleted; deactivate it instead.
Sale → MemberCascadeSame reasoning as subscriptions.
SaleItem → SaleCascadeLine items have no life of their own — a true composition.
SaleItem → ProductRestrictA sold product must remain resolvable for history/receipts.
Payment → MemberCascadePayment history belongs to the member.
Payment → SubscriptionNoActionForced by SQL Server. Member→Subscription→Payment and Member→Payment are two cascade paths into the same table; SQL Server rejects multiple cascade paths, so the subscription leg must be NoAction.
Inventory / StockMovement → ProductCascadeStock records are meaningless without their product.
Follow the thread all the way up. Because member deletes cascade, deleting a member would silently destroy their payments and sales. So MemberRepository.GetHistoryCountsAsync counts subscriptions + payments + sales, MemberService refuses the delete, and both UIs tell the user to set the status to Inactive instead. A database constraint drove a business rule, which drove a UI message. That is one coherent story across all four layers — it's the single best 90 seconds of your presentation.

7. Repository layer — generic + specific

7.1 The generic base

GenericRepository<T> implements the five operations every table needs, once, for all entity types:

public class GenericRepository<T> : IGenericRepository<T> where T : class
{
    protected readonly TenantErpDbContext _context;
    protected readonly DbSet<T> _dbSet;

    public GenericRepository(TenantErpDbContext context)
    {
        _context = context;
        _dbSet   = context.Set<T>();     // resolves the right table from the type
    }

    public virtual async Task<T?>       GetByIdAsync(int id) => await _dbSet.FindAsync(id);
    public virtual async Task<List<T>> GetAllAsync()        => await _dbSet.ToListAsync();

    public virtual async Task<T> AddAsync(T entity)
    { await _dbSet.AddAsync(entity); await SaveChangesAsync(); return entity; }

    public virtual async Task<T> UpdateAsync(T entity)
    { _dbSet.Update(entity); await SaveChangesAsync(); return entity; }

    public virtual async Task<bool> DeleteAsync(int id)
    {
        var entity = await GetByIdAsync(id);
        if (entity == null) return false;
        _dbSet.Remove(entity); await SaveChangesAsync(); return true;
    }
}

Note virtual on every method — derived repositories can override, and Set<T>() is what makes one class serve eleven tables. That is generics + the repository pattern doing real work.

Example worth quoting — server-side search

// Case-insensitive match across the fields shown in the member grid.
public async Task<List<Member>> SearchAsync(string term)
{
    if (string.IsNullOrWhiteSpace(term)) return await GetAllAsync();

    var pattern = $"%{term.Trim()}%";

    return await _dbSet
        .Where(m => EF.Functions.Like(m.FirstName, pattern) ||
                    EF.Functions.Like(m.LastName,  pattern) ||
                    EF.Functions.Like(m.Email,     pattern) ||
                    EF.Functions.Like(m.Phone,     pattern))
        .OrderBy(m => m.MemberId)
        .ToListAsync();
}

EF.Functions.Like translates to a SQL LIKE, so the database filters and only matching rows cross the wire — as opposed to pulling every member into memory and filtering with LINQ-to-Objects. Good "efficiency" talking point.

Expect the question: "Isn't the repository pattern redundant over EF Core, since DbSet is already a repository?" Your answer: it is a real debate. Here it earns its place because (a) services depend on IMemberRepository, so they can be unit-tested with a fake and no database; (b) query shapes like the three-table history count are defined once instead of being retyped in each caller; and (c) the two front ends provably share them. The cost is an extra layer of indirection, which you accept knowingly.

8.1 Business rule #1 — derived membership status

MemberService.GetMembershipOverviewAsync is a great slide because the status shown in the UI is computed, never stored:

public const int ExpiringSoonDays = 14;
…
// The subscription running furthest into the future decides the status.
var current = member.Subscriptions
    .Where(s => s.Status != "Cancelled")
    .OrderByDescending(s => s.EndDate)
    .FirstOrDefault()
    ?? member.Subscriptions.OrderByDescending(s => s.EndDate).FirstOrDefault();

var daysRemaining = (int)Math.Ceiling((current.EndDate.Date - today).TotalDays);

if      (current.Status == "Cancelled")        view.MembershipStatus = "Cancelled";
else if (daysRemaining < 0)                 view.MembershipStatus = "Expired";
else if (daysRemaining <= ExpiringSoonDays)  view.MembershipStatus = "Expiring Soon";
else                                        view.MembershipStatus = "Active";

// …then payment status from what has actually been paid against the plan price
var paid = await _paymentRepository.GetSubscriptionPaidTotalAsync(current.SubscriptionId);
view.Balance = Math.Max(0m, view.PlanPrice - paid);
view.PaymentStatus = paid <= 0m ? "Unpaid" : view.Balance > 0m ? "Partial" : "Paid";

Why this matters: a stored status column goes stale the moment a date passes. Deriving it means the grid is always correct without a nightly job. (The bulk ExpireOverdueSubscriptionsAsync exists to keep the persisted status column in sync for reporting, and the dashboard calls it first.)

8.2 Business rule #2 — the transactional sale

SaleService.CreateSaleAsync is the most complex operation in the system. Walk it as a sequence:

  1. Reject an empty basket; verify the member exists.
  2. Merge duplicate product lines by GroupBy(ProductId) so stock is checked against the true total, not line by line.
  3. Validate every line: quantity > 0, unit price ≥ 0.
  4. BeginTransactionAsync().
  5. Build the Sale with its SaleItems, accumulating TotalAmount.
  6. SaveChangesAsync() — the sale now has an identity value.
  7. For each line, DeductStockAsync: load inventory, throw if QuantityOnHand < quantity, decrement, and append a StockMovement with Reference = "SALE-{id}" and BalanceAfter.
  8. SaveChangesAsync(), then CommitAsync(). Any exception → RollbackAsync() and rethrow.
await using var transaction = await _context.Database.BeginTransactionAsync();
try
{
    … build sale, SaveChangesAsync() …

    // Stock only moves once the sale itself has an id to reference.
    foreach (var line in merged)
        await DeductStockAsync(line.ProductId, line.Quantity, sale.SaleId);

    await _context.SaveChangesAsync();
    await transaction.CommitAsync();
    return sale;
}
catch { await transaction.RollbackAsync(); throw; }
The demo that wins marks: try to sell 100 units of a product with 5 in stock. You get "Not enough stock for Protein Bar: 5 on hand, 100 requested" — and no sale row is created, because the transaction rolled back. That is ACID atomicity you can show on screen in ten seconds. Deleting a sale runs the mirror path: stock is returned with Reference = "VOID-{id}".

8.3 Business rule #3 — fair renewal

// Renewing early extends from the existing end date rather than losing paid-for days.
var renewFrom = subscription.EndDate > DateTime.UtcNow ? subscription.EndDate : DateTime.UtcNow;
subscription.StartDate = renewFrom;
subscription.EndDate   = renewFrom.AddMonths(plan.DurationMonths);
subscription.Status    = "Active";

Renew early and you keep your remaining days; renew after lapsing and the clock starts today. One ternary, one real-world policy — a good example of "business rule" that isn't just validation.

9. DTOs — what, why, and the full catalogue

9.1 What a DTO is

A Data Transfer Object is a flat, behaviour-free class whose only job is to carry data across a boundary — here, the HTTP boundary between ERP_api and its clients. They live in ERP_api/DTOs/.

9.2 Why not just return the entities?

The code answers this itself, in the header comment of ApiMappings.cs:

// Entities carry navigation properties in both directions, so returning them straight
// from an endpoint serialises the whole object graph. These projections keep the
// write endpoints returning the same shape their matching read endpoints do.

Four concrete reasons, in the order a panel will find convincing:

  1. Infinite recursion. Member.Subscriptions → Subscription.Member → Subscription.Subscriptions…. Serialising a raw entity either blows the cycle detector or dumps the entire database into one response.
  2. Over-posting / mass assignment. If POST /members bound directly to Member, a caller could set MemberId, JoinDate or CreatedAt themselves. CreateMemberDto exposes exactly four writable fields — the attack surface is the DTO, and nothing else is reachable.
  3. Contract stability. Rename an entity column and API clients keep working, because the DTO and the mapping absorb the change.
  4. Payload size. The client gets the seven fields it renders, not every audit column.

9.3 The three-DTO convention

Most resources have three DTOs, and the split is deliberate:

public class CreateMemberDto      // input for POST — no Id, no Status (server decides)
{ public string FirstName, LastName, Phone, Email; }

public class UpdateMemberDto      // input for PUT — adds Status, still no Id (it's in the URL)
{ public string FirstName, LastName, Phone, Email, Status = "Active"; }

public class MemberDto            // output — adds MemberId and JoinDate, which are server-generated
{ public int MemberId; public string FirstName, LastName, Phone, Email;
  public DateTime JoinDate; public string Status; }
Ask yourself "why three?" before the panel does: Create can't accept an Id (the database issues it) or a JoinDate (the server stamps it). Update can accept Status but still not an Id. Read must return both. Different directions permit different fields — one shared class would have to allow the union of all of them, which is precisely the over-posting hole.

Two patterns in that table deserve a callout:

  • UpdatePaymentStatusDto has exactly one property. It backs PATCH /payments/{id}/status — a partial update, distinct from a full PUT. Correct REST verb semantics.
  • StockAdjustmentDto, ReorderLevelDto, StockMovementRequestDto are commands, not rows. They model an intent ("adjust this product to 42 units, because…"), which is why they don't mirror any table.

9.5 Mapping — hand-written extension methods

public static class ApiMappings
{

Why not AutoMapper? A defensible answer: hand-written mapping is compile-time checked, has zero reflection cost, needs no extra package, and is trivially debuggable — at this project size the convention-based tool would add a dependency and a configuration-error failure mode without saving meaningful code. Mention that you considered it.

Five things happen in those six lines, and each is one bullet on a slide:

  1. Routing — the URL template binds the endpoint.
  2. Model binding — JSON body is deserialised into CreateMemberDto automatically.
  3. Dependency injection — IMemberService is resolved from the container per request; the endpoint never news up a service or a DbContext.
  4. Delegation — one call into the service. The controller contains no business logic.
  5. HTTP semantics — 201 Created plus a Location header pointing at the new resource, body projected through ToDto().

11.4 UPDATE

Selecting a grid row fires gridMembers_SelectionChanged, which stores _selectedMemberId and copies the row into the editable textboxes. btnUpdate_Click then: guards on _selectedMemberId == -1 → reads the form → calls UpdateMemberAsync(id, …). The service loads the entity first, mutates its properties, and calls UpdateAsync; EF's change tracker emits an UPDATE for the changed columns only. A null return means the row vanished between select and save, and the UI says "That member no longer exists — the list has been refreshed."

Note the small safety rule: Status = string.IsNullOrWhiteSpace(status) ? member.Status : status.Trim() — an empty status never wipes the existing one.

12.2 The clever bit — a DI scope per navigation

// Each module gets a dedicated DI scope so it works against its own DbContext and
// always reads the current database state rather than cached tracked entities.
private void Navigate<TForm>(string moduleName) where TForm : Form
{
    scope = _scopeFactory.CreateScope();
    var form = scope.ServiceProvider.GetRequiredService<TForm>();

    ReleaseCurrentModule();          // dispose previous form AND its scope

    form.TopLevel = false;
    form.FormBorderStyle = FormBorderStyle.None;
    form.Dock = DockStyle.Fill;
    pnlContent.Controls.Add(form);
    form.Show();

    _currentForm = form; _currentScope = scope;
}
This solves a bug most student WinForms projects ship with. A desktop app has no request boundary, so a single long-lived DbContext accumulates tracked entities and starts serving stale data — you edit a member in one screen and another screen keeps showing the old values. Creating a scope per navigation gives every module a fresh DbContext, which is the desktop equivalent of a web request scope. It also embeds the module form inside the shell panel (TopLevel = false + Dock = Fill) instead of opening separate windows, which is why FitCore feels like one application rather than a pile of dialogs.

Cardinality in words, for the script: a Member has many Subscriptions, many Sales and many Payments. A MembershipPlan has many Subscriptions. 19. Likely panel questions & answers

Is this MVC?

Not the ASP.NET MVC template — there are no server-rendered Views. It's a layered/Clean architecture where each front end applies an MVC-family pattern: WinForms fuses View and Controller in the Form class with the Model fully extracted; the API's minimal-API delegates are controller actions with JSON as the view; Blazor uses MVVM. The value is that all three drive the same Model.

Where are your controllers?

In ERP_api/Program.cs, as minimal-API endpoint delegates — same routing, DI and model binding as controller actions, less ceremony. WeatherForecastController is the scaffolded template, not part of the system. At 50 endpoints and 704 lines, the refactor I'd do next is grouping them into MapMemberEndpoints-style extension methods.

Why DTOs instead of returning entities?

Four reasons: entities have bidirectional navigation properties so serialising one drags the whole object graph (and can cycle); DTOs prevent over-posting by exposing only the writable fields; they keep the API contract stable when the schema changes; and they cut payload size. Concretely, CreateMemberDto has four fields, so a client cannot set MemberId, JoinDate or CreatedAt.

What's the difference between a DTO, an entity and a view model? You seem to have all three.

Deliberately. An entity is shaped by the database; a view model (MembershipView, SaleView, DashboardSummary) is shaped by a screen and holds computed values; a DTO is shaped by the wire. Three audiences, three shapes — collapsing them would couple the database schema to both the UI and the public API.

Why a repository layer when EF Core's DbSet is already one?

It's a genuine trade-off. Here it earns its keep: services depend on interfaces so they're unit-testable without a database; query shapes like the three-table history count are written once; and both front ends provably reuse them. The cost is an extra indirection, which we accepted knowingly.

How do you prevent a member's payment history from being destroyed?

Three layers. The schema cascades member→payments, so the database would delete them. MemberRepository.GetHistoryCountsAsync counts subscriptions, payments and sales; MemberService.DeleteMemberAsync returns HasHistory and refuses; and both UIs tell the user to set the status to Inactive. A constraint drove a rule which drove a message.

What happens if a sale fails halfway through?

CreateSaleAsync wraps everything in BeginTransactionAsync. If any line lacks stock, DeductStockAsync throws, we RollbackAsync, and neither the sale, its items, the inventory decrements nor the stock movements are persisted. I can demonstrate it by over-selling.

Why is Payment → Subscription NoAction when every other FK cascades?

SQL Server rejects multiple cascade paths into the same table. Member→Subscription→Payment and Member→Payment are two such paths, so one leg must be broken; we kept the cascade on the member side, since payment history belongs to the member.

Is membership status stored or computed?

Computed, in GetMembershipOverviewAsync, from the subscription with the furthest end date: Cancelled, else Expired if days remaining < 0, else Expiring Soon within 14 days, else Active. A stored column goes stale the instant a date passes. ExpireOverdueSubscriptionsAsync exists separately to keep the persisted column in sync for reporting.

Is your application thread-safe / how do you handle concurrency?

DbContext isn't thread-safe, which is why it's registered Scoped: one per HTTP request on the web, and one per module navigation on the desktop via IServiceScopeFactory.CreateScope(). In the UI, the _isBusy flag prevents double-submits. We do not yet have optimistic concurrency tokens — a rowversion column on Member and Subscription is the next step if two operators might edit simultaneously.

What about security?

Connection strings use Windows Authentication, so no passwords are embedded; the tenant registry stores a CredentialKey, not a password; DTOs block over-posting; and EF Core parameterises every query, so there's no SQL injection surface. The honest gap: the API has UseAuthorization() in the pipeline but no authentication configured and a permissive AllowAll CORS policy — both are development settings that must be closed before deployment. JWT plus role-based authorization is the planned next milestone.

How would you add a new module, say Trainers?

Seven steps, following the existing pattern: entity in ERP_domain; DbSet + a ConfigureTrainers method in TenantErpDbContext; ITrainerRepository/TrainerRepository inheriting GenericRepository<Trainer>; ITrainerService/TrainerService; register both in the two Program.cs files; dotnet ef migrations add AddTrainers and update; then add the form and the endpoints. The business logic is written once and both UIs can use it.

What would you improve given more time?

In priority order: authentication and role-based authorization; a unit-test project (the interface-based design makes the services mockable today, we just haven't written the tests); split Program.cs into endpoint extension methods; route the business modules through ITenantDbContextFactory so multi-tenancy is end-to-end; add optimistic concurrency tokens; add server-side paging on the grids; and replace the deprecated .WithOpenApi() calls.

Why two DbContexts?

They serve different lifecycles and databases. MasterErp is the tenant registry (Companies, CompanyDatabases, Devices) and changes rarely; TenantErp holds one company's business data. Each has its own migration history — which is why every dotnet ef command must pass --context, and why both projects implement IDesignTimeDbContextFactory.

Why is your desktop app async everywhere? It's single-user.

Because the UI thread must never block on I/O — a synchronous database call freezes the window. Every handler is async, awaits the service, and the _isBusy flag plus SetBusy() disables the controls while work is in flight. It also means the same service methods are directly reusable by the API, which genuinely needs async for throughput.
